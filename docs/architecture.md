# Pledge — architecture

How the app, its four native extensions and the backend fit together, what
Apple lets us do, how to build, and the traps already walked into.

## Stack

- Expo SDK 51, React Native 0.74.5, bare workflow with `ios/` generated by
  prebuild and gitignored. Hermes. Old architecture.
- Node 20 (`/opt/homebrew/opt/node@20/bin`), Xcode 26.6 (SDK 26.5),
  CocoaPods 1.16, `patch-package` on postinstall.
- Navigation: `@react-navigation/stack` with a custom crossfade.
- Animation: `react-native-reanimated` 3.10 for pressables and the
  surrender modal; `Dissolve` and screen transitions use React Native's
  own `Animated` on the native driver. Video: `expo-av`.
- Screen Time: `react-native-device-activity` 0.4.13 (its config plugin
  generates three extension targets) plus two local Expo modules and one
  hand-written extension target.
- Auth: Firebase web SDK (project `pledgetrial`) with Sign in with Apple
  (`expo-apple-authentication`). Google sign-in was removed on 8 Nov 2026;
  email sign-in goes with the v2 opener.
- Payments: `@stripe/stripe-react-native` PaymentSheet in setup mode; the
  backend charges off-session later.
- Push: `expo-notifications` for local notifications and the APNs token.
- Backend: Hono on Vercel Functions (`backend/`), Firebase Admin, Stripe,
  APNs over HTTP/2, one daily cron.

## The five targets

| Target | Kind | Does |
| --- | --- | --- |
| Pledge | app | everything the user touches |
| ActivityMonitorExtension | DeviceActivityMonitor | runs the schedule even when the app is closed: at each threshold event executes stored actions (block the selection, post a notification); at interval start lifts the block |
| ShieldConfiguration | ManagedSettingsUI | draws the block screen from the config stored in the App Group |
| ShieldAction | ManagedSettingsUI | handles the two shield buttons: dismiss, or post the "unlock" notification |
| ReportExtension | DeviceActivityReport (ExtensionKit) | draws the 7-day total and top apps inside a sandbox; the host app only sees pixels |

All share App Group `group.com.pledgecompany.pledge`; the library passes
config through its UserDefaults. All five need the Family Controls
entitlement, and for App Store builds each App ID needs Apple's
per-App-ID "Family Controls (Distribution)" approval (all granted; see
`docs/release.md`).

The report extension must be an ExtensionKit extension (product type
`com.apple.product-type.extensionkit-extension`, `EXAppExtensionAttributes`
in Info.plist, embedded in `Pledge.app/Extensions/`). The patch in
`patches/@kingstinct+expo-apple-targets+0.1.19.patch` teaches the target
generator a `device-activity-report` type that does this. App Store
processing rejects the NSExtension form (ITMS-91179) even though dev builds
run it.

## How a pledge is enforced

1. The picker returns an opaque `familyActivitySelection` token (base64).
   The app never knows which apps are in it; the labels module can draw
   them, nothing else.
2. `startPledgeMonitoring` (`home.controller.ts`) stores the selection under
   `sel<id>`, the shield under `shield<id>`, and registers a daily
   DeviceActivity schedule `Pledge<id>` (midnight to midnight) with:
   - tick events every 5 min (`tick<n>`), used to show today's usage;
   - `limitReached` at the daily limit, whose action is `blockSelection`
     with that shield; limit 0 blocks from interval start;
   - six more ticks past the limit (limit+5 ... limit+30) that also block;
   - `intervalDidStart` unblocks, so the block lifts at midnight.

   The block actions are unconditional. Build 25 guarded them (a block ran
   only if the previous event fired at least 60 s earlier), to stop iOS
   firing the limit early (Apple FB15103784, FB18061981; one field report of
   "limit reached" at 26 of 60 minutes). On the owner's phone the limit then
   never blocked: iOS delivers threshold events in bunches, so the guard
   skipped real limits too. Removed in build 26. Time iOS counts, including
   from other devices on the same Apple ID, blocks. Home rewrites the block
   actions on every load (`configureLimitActions`), so schedules from older
   builds pick up the current actions without restarting; schedules from
   before build 25 lack the ticks past the limit until restarted.
3. Usage today is read from the library's event store (`getTodayUsage`):
   the highest tick that fired, in 5-min steps. The limit counts as reached
   once any blocking event fired today, and then shows as the full limit.
   Long-press "Today" on the pledge screen lists today's events with the
   time each fired, for diagnosing reports like the one above.
4. The shield's "Unlock" cannot open an app (Apple), so it posts a local
   notification with `{action: "unlock", pledgeId}`. Home reads the
   response and open the surrender modal for that pledge.
5. Surrender: `POST /stripe/charge {pledgeId}` → backend charges the saved
   payment method off-session → app stops monitoring and removes the
   pledge. Completion: `POST /pledge/:id/complete`.
6. Paid break: `POST /stripe/break {pledgeId, day}` → backend reserves one
   of the day's 3 slots in a transaction on the pledge doc (`breaks.{day}`),
   charges $1 off-session (idempotency key per slot), gives the slot back
   if the card fails. The app then unblocks the selection and starts
   `Break{id}`: non-repeating, from 10 min ago to 5 min from now (Screen
   Time refuses schedules under 15 min; a window that already started
   begins at once), with `blockSelection` on `intervalDidEnd`, so the apps
   lock again on the clock with Pledge closed. Skipped when the end falls
   after midnight. `isOnBreak` (started < 5 min ago) keeps
   `reassertBlocks` from re-blocking a pledge mid-break.

Several pledges run side by side; every name is derived from the 10-char
id and ids must be fixed length (the library clears events by prefix).
Names must not contain underscores.

Blocks are not per pledge: the library keeps one blocklist for the whole
device, and unblocking a selection subtracts its apps from it. Two
pledges that share an app would unblock each other, so after a pledge
ends (surrender, completion, forfeit) `reassertBlocks` re-blocks every
remaining pledge already over its limit today, and Home does the same on
every load. Gap: at midnight each pledge's extension unblocks its own
selection; a 0-minute pledge sharing apps with another may come out
unblocked until Pledge is next opened.

## Deletion and revocation detection

Apple gives no uninstall callback, so:

- The app registers its APNs token (`POST /device`) and sends a heartbeat
  (`POST /heartbeat {screenTimeAuthorized}`) on every foreground. A
  heartbeat with Screen Time revoked forfeits active pledges immediately.
- Vercel cron `GET /cron/check-devices` (09:00 UTC, bearer `CRON_SECRET`)
  sends a silent push to every device of every user with an active
  pledge. APNs answering `410 Unregistered` means the app is gone → the
  backend charges and marks the pledges `forfeited` with reason
  `app_deleted`. Failed charges keep the pledge active with `chargeError`
  and retry next run.
- `aps-environment` is `development` in `app.json`; EAS/Xcode flip it to
  production for store builds. The backend talks to the APNs host that
  matches the token's environment.

## Backend (`backend/`, Vercel project `pledge-backend`)

Live at https://pledge-backend-weld.vercel.app. Every route except `/`,
`/health`, `/terms`, `/privacy`, `/stripe/publishable-key` and the cron
needs `Authorization: Bearer <Firebase ID token>`.

| Route | Does |
| --- | --- |
| `POST /auth/firebase/signup` | creates the user doc |
| `POST /stripe/payment-sheet` | customer + ephemeral key + SetupIntent for PaymentSheet |
| `GET /stripe/payment-method` | whether a card is on file (skips the card step) |
| `POST /pledge` | records a pledge (idempotent on id); validates amount 1–100 |
| `GET /pledges` | the user's pledges |
| `POST /pledge/:id/complete` | marks completed |
| `POST /stripe/charge` | charges a pledge (surrender) |
| `POST /device`, `POST /heartbeat` | deletion detection (above) |
| `GET /cron/check-devices` | daily silent-push sweep |

Firestore: `users/{uid}` (profile, `stripeCustomerId`, `lastHeartbeatAt`,
`screenTimeAuthorized`), `users/{uid}/pledges/{id}` (`status`
active/surrendered/completed/forfeited, amounts, `endsAt`,
`paymentIntentId`, `forfeitReason`, `chargeError`), `users/{uid}/devices/{token}`.

Env (see `backend/.env.example`): `STRIPE_SECRET_KEY`,
`STRIPE_PUBLISHABLE_KEY` (sandbox keys on Vercel right now; live keys
must go back before launch), `FIREBASE_SERVICE_ACCOUNT` (JSON or base64),
`PLEDGE_CURRENCY=usd`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_KEY_P8`
(base64), `APNS_BUNDLE_ID`, `CRON_SECRET`. All set in Vercel production as
Sensitive. Local dev: `backend/.env` (gitignored), `npm run dev` on :3000.

Deploy: the owner runs `cd backend && vercel --prod --yes`. Agents cannot.

## App configuration

- `app.json`: version 1.1.0, build number auto-incremented by EAS and
  committed; bundle `com.pledgecompany.pledge`; team GC2XRZ6HSJ; iOS
  deployment target 16.0; `useFrameworks: static`; plugins listed there.

## Analytics (PostHog)

`src/services/analytics.ts`, PostHog US cloud (`us.i.posthog.com`), SDK
`posthog-react-native` with `expo-device` / `expo-application` for device
and app properties; storage falls back to AsyncStorage (no
`expo-file-system`). The project key is public by design and lives in
`src/config.ts` (`EXPO_PUBLIC_POSTHOG_KEY` overrides; empty disables).

- `PostHogProvider` in `App.tsx`, inside `NavigationContainer`
  (react-navigation v6), autocaptures every screen and every tap with the
  tapped text. Typed text is never captured.
- App lifecycle events (installed, updated, opened, backgrounded) are on.
- Users are identified by Firebase uid with email and name as person
  properties (`onAuthStateChanged`); reset only on a real sign-out.
- Every event carries `build: dev | release`; filter `release` for real
  numbers.
- Named events (the `AnalyticsEvent` union) mark funnel steps: opener
  states, sign-up/in by method, `deal_finished`, `pledge_step_viewed` per
  wizard step (the steps are one screen, so screen tracking can't see them),
  Screen Time authorization, apps selected, terms, card, pledge started or
  failed, breaks, surrender, completion, forfeit.
- Never send Screen Time data (which apps, usage, threshold timings): the
  privacy policy promises usage stays on the device, and Apple restricts it.
- Privacy policy (`backend/src/legal.ts`) lists in-app activity and PostHog.
  The App Store privacy label must also declare Product Interaction and
  Device ID / User ID linked to the user, used for Analytics, not tracking.

## Apple limits that shape the product (explain, don't fight)

- The app never learns which apps were chosen, how much they were used, or
  the 7-day total. Only the report extension can see usage, and it can only
  draw; it has no network and cannot talk to the host app. So no usage data
  reaches the backend or any agent.
- Shield extensions cannot open apps or make network calls reliably; the
  unlock path goes through a notification.
- Website selections only cover Safari; Private Browsing escapes. Category
  picks are Apple's categories (Instagram is "Social", not "Entertainment").
- Schedules are per day in device local time; the finest usage event the
  monitor gets is the thresholds we register (hence 5-min ticks).
- An agent cannot set apps on the user's behalf; it can change hours and
  limits by pushing a new schedule to the app for it to register.
- None of this works in the simulator; use the owner's phone.
- Two DeviceActivityReport views share one extension process; rendering
  two at once made one blank. Hence one `overview` context per screen and
  a fresh identity (`generation`) on every render.
- The extension takes parameters only through the App Group. The
  `recovered` context (Home's time back) reads `pledgeReport.recovered.anchorMs`
  and `pledgeReport.recovered.selection` (the union of the pledges'
  selections, JSON-encoded by `PledgeActivityReportView`), queries the whole
  iPhone with no app filter and matches tokens itself, so one query gives
  both the pledged apps and the phone's total. Report views start in their
  final state and only reset for the animation in `onAppear`: a view that
  never animates must still show its numbers.

## Dev loop

```sh
export PATH="/opt/homebrew/opt/node@20/bin:$PATH"
npx expo start --dev-client --tunnel        # Metro; the dev build connects to it
# native change:
npx expo prebuild --platform ios --no-install   # add --clean if a target changed shape
(cd ios && pod install)
xcodebuild -workspace ios/Pledge.xcworkspace -scheme Pledge -configuration Debug \
  -destination id=00008150-00154C280AD8C01C -derivedDataPath <scratch>/DerivedData \
  -allowProvisioningUpdates -allowProvisioningDeviceRegistration build
xcrun devicectl device install app --device 00008150-00154C280AD8C01C <DerivedData>/Build/Products/Debug-iphoneos/Pledge.app
```

`-configuration Release` builds the embedded-bundle app for checking
release-only behaviour. Store builds: `docs/release.md`.

Check a built app has all extensions: `ls Pledge.app/PlugIns` (three) and
`ls Pledge.app/Extensions` (ReportExtension.appex with
`EXAppExtensionAttributes` in its Info.plist).

Wiping a test account (Firestore + Auth) is a scratch script the owner
runs; agents are not allowed to run deletions.

## Known issues and gotchas

- **Blank first pledge step on TestFlight (build 20, fixed in source
  29 Oct 2026, ships with the next build).** Several testers saw the dots
  and the Continue/Cancel pill but no question or content on the first
  pledge step (one report: iPhone 17 Pro, iOS 26.6.2, dark ground uniform,
  so nothing was drawn over it). The step content lived in `Dissolve`, a
  Reanimated `Animated.View` with `entering={FadeIn.delay(160)}`: the
  entering animation applied opacity 0 and never progressed, so the view
  stayed invisible. Not reproduced on the owner's phone (iOS 26.6.1) and
  the same wrapper worked on the opener for those testers, so the trigger
  is specific to that screen (it asks for Screen Time access the moment it
  mounts, and `steps` can change right after mount). `Dissolve` now
  renders visible and animates only on `id` change, with React Native's
  `Animated` on the native driver, the same machinery as the screen
  transitions, which did complete on the affected phones. Never again
  gate first paint on a layout animation. The surrender modal still uses
  Reanimated `entering`; if it ever comes up blank, do the same there.
- `PressableScale` sets `opacity` in its animated style, which overrides a
  caller's opacity; it now multiplies by the flattened style's opacity so
  disabled buttons dim. Keep that when touching it.
- iOS caches launch screens: an old splash can flash after a change until
  reinstall + reboot.
- EAS ignores `.gitignore`; `.easignore` decides what is uploaded, and its
  matcher cannot re-include under `targets/*`. A root-only pattern is
  written `/firebaseConfig.js`; a bare name also matched `src/firebaseConfig.js`
  and broke a build.
- Xcode 27 images fail on pod deployment targets < 15 and need the scene
  lifecycle on iOS 27; stay on the Xcode 26.6 image until the Expo SDK
  upgrade. The pod hook is already in place for later.
- Changing a target's product type needs `prebuild --clean` or the
  project ends up with duplicate targets.
- `react-native-device-activity` encodes events as
  `events_{activity}_{callback}_{event}` and splits on `_`: no underscores
  in any name.
- Pledge ids are 10 chars, fixed length, because clean-up is by prefix.
- Terms/Privacy must open in `expo-web-browser`'s sheet; `Linking.openURL`
  to the backend was refused on device.
- Days-left must use ceil in both the card and the detail or they disagree.
- Opening the app picker twice in a row needs a fresh key on the picker.
